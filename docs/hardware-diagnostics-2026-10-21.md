# Диагностика USB подключения NeuroCube

Дата: 21 октября 2026 года. Плата: Waveshare RP2350-Touch-LCD-1.54 с установленным аккумулятором.

Устройство обнаружено и доступно Windows через USB. Найден один подходящий экземпляр; пользователь подтвердил, что это NeuroCube. Текущая прошивка предоставляет CDC и служебный интерфейс Reset. Режим BOOTSEL сейчас не активен.

Диагностика выполнена без прошивки, сброса, перезагрузки, открытия COM-порта, отправки команд устройству и изменения его содержимого. Управление питанием и аккумулятором не затрагивалось. На этапе диагностики репозиторий не изменялся; этот файл добавлен позднее по отдельному запросу пользователя.

## 1. Обнаружение устройства

Идентификация основана на VID/PID, серийном номере, классах интерфейсов и принадлежности дочерних устройств одному USB-родителю.

| Параметр | Значение |
|---|---|
| VID | `0x2E8A`, Raspberry Pi |
| PID | `0x0009`, Pico SDK CDC UART |
| USB Product | `Pico` |
| Серийный номер | `419CB819454EA93D` |
| InstanceId | `USB\VID_2E8A&PID_0009\419CB819454EA93D` |
| Состояние PnP | `OK`, ProblemCode `0` |
| Подключение | Контроллер xHCI, USB Root Hub, порт 4 |
| LocationPath | `PCIROOT(0)#PCI(1400)#USBROOT(0)#USB(4)` |
| ContainerId | `{4A613A56-41D1-5417-8D51-CAFD8D8752F9}` |

PID `0009` выделен для Pico SDK CDC UART. Он подтверждает тип USB-конфигурации, но не является уникальным идентификатором модели Waveshare. Принадлежность платы проекту подтверждена пользователем. [Реестр PID Raspberry Pi](https://github.com/raspberrypi/usb-pid).

## 2. Идентификация в Windows

Родительское устройство определяется как `USB Composite Device`, служба `usbccgp`.

| Интерфейс | Имя Windows / USB | Драйвер | Состояние |
|---|---|---|---|
| `MI_00`, CDC | `USB Serial Device (COM3)` / `Board CDC` | Microsoft `usbser`, `usbser.inf` | OK |
| `MI_02`, vendor-specific | `Reset` | Microsoft WinUSB, `winusb.inf` | OK |

InstanceId CDC:

```text
USB\VID_2E8A&PID_0009&MI_00\6&3A05E353&0&0000
```

InstanceId Reset:

```text
USB\VID_2E8A&PID_0009&MI_02\6&3A05E353&0&0002
```

Совместимые идентификаторы CDC включают `USB\Class_02&SubClass_02&Prot_00`. Reset имеет `USB\MS_COMP_WINUSB` и `USB\Class_ff&SubClass_00&Prot_01`. Оба интерфейса связаны с указанным родителем и ContainerId. Драйверы подписаны; драйвер CDC версии `10.0.17763.8880`, WinUSB — `10.0.17763.9020`.

## 3. Текущий режим подключения

Рабочий режим прошивки с USB CDC. Набор дескрипторов `Pico`, `Board CDC`, `Reset` соответствует стандартной конфигурации Pico SDK. Название, версия и функциональность текущей прошивки неизвестны.

BOOTSEL не обнаружен: устройства `2E8A:000F`, USB Mass Storage и диска платы нет. PID `000F` выделен для загрузчика RP2350. Буква диска устройству не назначена.

Источники: [дескрипторы Pico SDK](https://github.com/raspberrypi/pico-sdk/blob/master/src/rp2_common/pico_stdio_usb/stdio_usb_descriptors.c), [реестр USB PID](https://github.com/raspberrypi/usb-pid).

## 4. Доступные интерфейсы

- **CDC / COM3:** транспорт обнаружен, драйвер установлен. Протокол и наличие потока логов пока неизвестны.
- **Reset / WinUSB:** служебный интерфейс обнаружен, драйвер установлен. Это не отладчик.
- **Mass Storage / UF2:** в текущем режиме отсутствует.
- **USB-отладчик SWD/CMSIS-DAP:** не обнаружен.
- **Другие USB-интерфейсы платы:** в PnP не обнаружены.

Отсутствие USB-отладчика не устанавливает доступность физических SWD-контактов на самой плате.

## 6. Возможность автоматической прошивки

Есть основания для автоматизации, но полный процесс не проверен.

Стандартный Reset-интерфейс с WinUSB указывает на потенциальную возможность программного перехода в BOOTSEL. Наличие дескриптора не гарантирует обработку команды: она зависит от параметров сборки текущей прошивки. Pico SDK предусматривает такой механизм; picotool поддерживает взаимодействие с совместимыми работающими прошивками.

Сейчас автоматическая прошивка не готова: picotool отсутствует, переход в BOOTSEL не проверялся, драйвер загрузочного интерфейса и ограничения записи неизвестны. Проверить весь процесс без изменения режима устройства невозможно. Команды сброса, режим принудительного перехода picotool и запись UF2 не выполнялись.

Источники: [реализация USB Reset](https://github.com/raspberrypi/pico-sdk/blob/master/src/rp2_common/pico_usb_reset/usb_reset.c), [picotool](https://github.com/raspberrypi/picotool).

## 7. Возможность получения диагностики

Транспорт COM3 есть; наличие диагностических данных не подтверждено. Порт может передавать логи или прикладной протокол, если это предусмотрено текущей прошивкой. Неизвестны формат данных, команды, параметры линии и регулярность вывода.

COM-порт не открывался: открытие может менять DTR/RTS и параметры линии. Pico SDK также предусматривает перевод в BOOTSEL по специальной скорости; автоматический перебор скоростей исключён. [Реализация USB Reset](https://github.com/raspberrypi/pico-sdk/blob/master/src/rp2_common/pico_usb_reset/usb_reset.c).

Без изменения прошивки уже доступны обнаружение платы, чтение PnP-метаданных и отслеживание подключения. Чтение логов возможно только при наличии вывода в текущей прошивке и после определения безопасных параметров подключения. USB-дескрипторы не предоставляют показания аккумулятора, зарядки, IMU или состояние экрана.

## 8. Действия пользователя и следующий этап

Для завершённой диагностики обнаружения дополнительных действий не требуется.

Для следующего этапа нужны исходники либо сведения о текущей прошивке: это поможет определить безопасные параметры CDC и доступные команды. После этого можно отдельно разрешить пробное чтение COM3 без отправки прикладных команд.

Для разработки потребуются Pico SDK, CMake, Ninja, ARM GCC и picotool; для Python Bridge — pyserial. Установка относится к следующему этапу. Ручной вход в BOOTSEL потребуется только если программный переход окажется недоступен. С установленным аккумулятором простое отключение USB не следует считать гарантированным сбросом платы.

## 9. Архитектура Hardware Bridge

Предлагается отдельный локальный процесс Windows на Python:

```text
Codex -> локальный API / MCP -> Hardware Bridge -> USB CDC -> NeuroCube
                                     |
                                     +-> picotool -> BOOTSEL
```

Требования к будущей реализации:

1. Обнаруживать плату по VID/PID и серийному номеру; определять COM-порт через PnP, не фиксировать `COM3` в коде. При неоднозначности возвращать список устройств.
2. Разделить обнаружение, чтение телеметрии, прикладные команды и обновление прошивки. По умолчанию разрешать только обнаружение и чтение метаданных.
3. Исключить автоматические reset, BOOTSEL, перебор скоростей и неизвестные команды при подключении.
4. Для будущей прошивки определить версионированный протокол с идентификацией, перечнем возможностей, версией сборки, телеметрией и ID запросов.
5. Сделать Bridge единственным владельцем COM-порта. Предусмотреть тайм-ауты, журналирование, восстановление подключения и переходные состояния при смене USB-режима.
6. Обновление вынести в отдельный сценарий: выбор устройства и образа, явное разрешение, BOOTSEL, запись с проверкой, повторное обнаружение. Соответствие устройства между режимами проверять повторно; номер COM-порта и PID могут измениться.
7. Исключить управление питанием и аккумулятором из доступных по умолчанию команд. Не подставлять параметры GPIO и индикации сброса без проверки схемы платы.

USB-подключение исправно; CDC и WinUSB обеспечены установленными драйверами Windows. Следующий этап — определить происхождение текущей прошивки и безопасно проверить диагностический вывод.
