# Codex task: устойчивое управление документацией NeuroCube

## Цель
Закрепить в репозитории правила, которые сохраняют стратегическую документацию чистой и полезной для новых разработчиков и агентов. НЕ переписывать проект с нуля и НЕ менять код прошивки в рамках этой задачи.

## Источники
Прочитать README.md, docs/product-vision.md, docs/architecture.md, docs/hardware.md, AGENTS.md, docs/backlog.md, CHANGELOG.md, docs/progress.md, docs/codex-final-polish-2026-10-21.md и текущую структуру docs/.

## Информационная архитектура
- README.md: вечнозелёная точка входа — цель, возможности, целевая платформа, концепция, ссылки на основные документы и краткий воспроизводимый quick start. Без датированных багов, статусов P0, оперативных дедлайнов, разовых результатов тестов или PR.
- docs/product-vision.md: долгосрочные продуктовые цели, наборы игр, механики, UX, пользовательский опыт, персонализация, словарь Magic Ball, направления развития. Не содержит инцидентов, временных блокеров, планов конкретной ночной итерации.
- docs/architecture.md: актуальные технические решения, контракты, слои, способ добавления игр; описание «как устроено», а не список дефектов.
- docs/hardware.md: стабильные аппаратные факты, схемы, пины, ограничения; временные симптомы/инциденты — в backlog, а не в аппаратной спецификации (при этом не удалять важные диагностические свидетельства).
- AGENTS.md: обязательные для агентов правила и маршрут чтения; короткий, недвусмысленный, без ссылок на устаревающие разовые задачи как единственный источник требований.
- docs/backlog.md: открытые баги, задачи, приоритеты, критерии приёмки, ссылки на доказательства; статус каждой задачи должен обновляться, не считать запись выполненной по факту коммита.
- CHANGELOG.md: только фактически внесённые изменения, структурированные по версиям или Unreleased; не писать в нём план или неподтверждённое исправление.
- docs/progress.md: текущий технический статус, что подтверждено на реальном устройстве/симуляторе/сборкой, оставшиеся ограничения; может быть датированным.
- docs/tasks/ и docs/evidence/: исторические задания, отчёты и результаты диагностики, ссылки из backlog/progress; не терять исходные наблюдения.

## Что выполнить
1. Провести аудит пересечений и противоречий между документами. Исправить навигацию, устаревшие ссылки и дублирование, сохранив все продуктовые решения и фактические сведения.
2. Закрепить таблицу ответственности документов и правило «куда писать новый факт» в docs/documentation-policy.md.
3. Обновить AGENTS.md: при изменении функциональности агент обязан обновить соответствующий backlog/progress/changelog; менять README/vision только при осознанном изменении стратегических решений. Новые игры документировать в vision при изменении каталога, в architecture при изменении контракта, в changelog после реализации.
4. Проверить, что сведения об инциденте автономного питания, проблеме калибровки, обрезании текста, UX игр и визуализации Magic Ball находятся в backlog, а не в README/vision. Сохранять ссылку на первичные диагностические документы. Текущий статус определять по проверкам, не гадать.
5. Сохранить в product-vision.md персонализацию «Привет, Андрей», три сета по четыре игры, Magic Ball с двумя связанными фразами и утверждённым словарём, включая «Нужна перезагрузка». Не добавлять год рождения.
6. Проверить относительные Markdown-ссылки и доступность целевых файлов; добавить лёгкую автоматическую проверку структуры/ссылок, если возможно без тяжёлых зависимостей.
7. Избегать ссылок из стратегических документов на разовые документы как на обязательный долгосрочный источник истины. Исторические задания не удалять, можно помечать архивными.
8. Не изменять исходный код, конфигурацию питания, USB и сборку без отдельной причины и разрешения. Не прошивать плату.
9. Работать в codex/neurocube-mvp, не делать force push и не мержить PR. Коммитить и push изменения, обновить существующий PR. Не перезаписывать незакоммиченные изменения пользователя.

## Критерии приёмки
- Новый разработчик за 5 минут по README понимает продукт и находит архитектуру, hardware, статус и backlog.
- В README и vision нет оперативных дефектов, датированных P0 и разовых результатов приёмки.
- Backlog хранит актуальные открытые задачи; changelog содержит только изменения; progress содержит проверяемые статусы.
- Правила документации закреплены в AGENTS.md и docs/documentation-policy.md.
- Ссылки и навигация проверены, продуктовые решения не потеряны.
- Финальный отчёт содержит перечень изменённых файлов, найденных расхождений и commit/PR ссылки.
