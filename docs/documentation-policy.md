# Политика документации NeuroCube

Документация — долговременная база знаний. Каждый факт имеет основной документ; в других местах оставляют ссылку и необходимое краткое пояснение. Намерение, выполненное изменение и проверка — разные сведения.

## Ответственность документов

| Документ | Что хранить | Что выносить в другое место |
|---|---|---|
| [README](../README.md) | Цель, платформа, возможности, маршрут чтения, воспроизводимый quick start | Дедлайны, P0, разовые тесты, PR и инциденты |
| [product-vision](product-vision.md) | Продуктовый замысел, каталог, механики, UX, персонализация, словарь Magic Ball | Текущие ограничения, отладка, ночные планы |
| [architecture](architecture.md) | Реальные слои, контракты, решения, расширение | Открытые дефекты, результаты отдельных прогонов |
| [hardware](hardware.md) | Подтверждённые схемы, пины, полярности, ограничения и область Flash | Временные симптомы и результаты конкретного устройства |
| [AGENTS](../AGENTS.md) | Обязательный маршрут и инженерные правила | Дублирование всего замысла или одноразового задания |
| [backlog](backlog.md) | Текущие задачи, дефекты, приоритет, статус и критерий закрытия | Подробную историю уже выполненных изменений |
| [CHANGELOG](../CHANGELOG.md) | Реально внесённые изменения по версиям/датам | Планы и неподтверждённое заявление «исправлено на плате» |
| [progress](progress.md) | Текущая реализация, установленный/собранный коммит, результаты и границы проверки | Полную копию требований или словаря ответов |
| [tasks](tasks/README.md) | Утверждённые задания и их исторический контекст | Автоматический статус «сделано» по наличию файла |
| [evidence](evidence/README.md) | Датированные отчёты, первичные наблюдения, логи, хеши и изображения | Новые обязательные продуктовые правила |
| [player-guide](player-guide.md), [build](build.md), [bridge](bridge.md) | Практические инструкции для текущего поведения | Несуществующие функции и неподтверждённые возможности |

## Куда писать новый факт

- Новая цель или согласованная механика: vision; реализацию планировать в backlog. Не подгонять замысел под дефект кода.
- Новый баг: backlog с наблюдаемым поведением, ожидаемым результатом, приоритетом и ссылкой на evidence. В README его не переносить.
- Изменение кода: CHANGELOG о сделанном, progress о состоянии, backlog о следующем требуемом доказательстве. Коммит сам по себе не закрывает аппаратную приёмку.
- Новый тест: evidence с датой, версией/коммитом, источником ввода, способом проверки и ограничениями; краткий итог в progress.
- Новая игра: vision при изменении каталога, architecture при изменении контракта, player-guide для реализованного управления, CHANGELOG после реализации.
- Новые данные о GPIO: hardware только после сверки конкретной схемы; диагностику конкретного прогона сохранить в evidence.

## Доказательства и статусы

Использовать `VERIFIED_ON_HARDWARE`, `VERIFIED_IN_SIMULATOR`, `COMPILED_ONLY`, `NOT_TESTED`. Для аппаратного статуса указывать, что проверено: электронный обмен, синтетический ввод или физическая проверка человеком. USB и framebuffer не доказывают работу сенсора, видимый LCD, автономность или wake.

Задача проходит состояния: открыта → реализована → проверена программно → ожидает аппаратной приёмки → принята, если её критерий требует плату. Закрытие требует ссылки на достаточные доказательства. Частично принятый пункт разделять на выполненную и оставшуюся части.

## История и разрешение противоречий

Текущие явные указания пользователя имеют приоритет. Долгосрочный продуктовый источник — vision, технические факты — architecture/hardware, действующие задачи — backlog. Датированное задание не становится вечной нормой. При новом явном изменении требований обновить основной документ и записать решение; при обычном дефекте сохранить замысел.

Первичные задания/отчёты не удалять. Старые корневые документы docs сохраняются по прежним адресам и помечаются историческими; новые задания размещать в tasks, отчёты — в evidence. Из исторического документа вести ссылку на актуальный статус. Не переписывать прошлые результаты под сегодняшнюю прошивку.

## Проверка перед коммитом

1. Обновить документы согласно таблице ответственности; убрать дублирующиеся источники истины.
2. Проверить, что README и vision не содержат оперативных багов, результатов тестов и PR.
3. Запустить `python docs/tools/check_docs.py`: локальные Markdown-ссылки, файлы, якоря и базовая структура. Для новых внешних ссылок проверить целевой официальный ресурс; приватный GitHub может требовать авторизацию.
4. Проверить diff: не потеряны механики, «Привет, Андрей», три сета по четыре игры, 24 пары Magic Ball и «Нужна перезагрузка».
5. Не коммитить токены, личные резервные копии и двоичные сборки. Галереи и обезличенные технические свидетельства хранить с объяснением происхождения.
